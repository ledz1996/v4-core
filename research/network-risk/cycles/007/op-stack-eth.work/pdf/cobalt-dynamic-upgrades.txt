Cantina is a security platform that pairs a world-class network of security researchers with agentic AI
to help teams building onchain find and fix real risk. Through managed reviews, competitions, and

1.2     Disclaimer
Cantina Managed provides a detailed evaluation of the security posture of the code at a particular
moment based on the information available at the time of the review. While Cantina Managed endeavors
to identify and disclose all potential security issues, it cannot guarantee that every vulnerability will
be detected or that the code will be entirely secure against all possible attacks. The assessment
is conducted based on the specific commit and version of the code provided. Any subsequent
modifications to the code may introduce new vulnerabilities that were absent during the initial review.
Therefore, any changes made to the code require a new security review to ensure that the code
remains secure. Please be advised that the Cantina Managed security review is not a replacement for
continuous security measures such as penetration testing, vulnerability scanning, and regular code
reviews.

3.1     High Risk
3.1.1   Untrusted RollupConfig can drive noncanonical proof execution under a canonical public
        commitment
Severity: High Risk.
Context: boot.rs#L264-L289.

Description: The proof host supplies a serialized RollupConfig through the local pre-image oracle.
Current implementation accepts this complete configuration after validating only that its l2_chain_
id matches the boot chain ID.

The complete configuration is subsequently used for L2 derivation. However, the public rollupConfig
Hash is calculated from crates/proof/primitives/src/per_chain_config.rs:127 , which omits
derivation-critical fields such as:
      • batch_inbox_address

      • seq_window_size

      • max_sequencer_drift
      • Channel timeouts.
      • Blob configuration.
      • protocol_versions_address
      • L1 chain ID and fee configuration.
Additionally, crates/proof/primitives/src/per_chain_config.rs:205 normalizes block_time and
the genesis L2 block number before hashing. scheduleId only commits upgrade activation times-
tamps and therefore does not cover these static parameters.
Consequently, it is possible to construct configurations C and C′ such that:

    rollupConfigHash(C) == rollupConfigHash(C′)
    scheduleId(C)       == scheduleId(C′)
    Derive(C, L1Data)   != Derive(C′, L1Data)


A malicious or compromised proof host can copy the canonical configuration, modify an omitted field,
and provide it to the guest. The zkVM then legitimately proves execution under the modified rules,
while its public output carries the expected canonical commitment. This is not a failure of SNARK
soundness; the proven statement does not sufficiently bind the executed configuration.
The Nitro path has the same trust mismatch: it executes using boot_info.rollup_config , but obtains
the signed crates/proof/tee/nitro-enclave/src/server.rs:149 .
A compromised authorized prover could therefore potentially produce an accepted proof or enclave
signature for a noncanonical output root, affecting disputes and any downstream state-root accep-
tance or withdrawal mechanism.
This affects versions that load oracle-supplied configurations for built-in chains. Base v1.2.0 does not
contain that behavior for known Base chain IDs.

3.2   Medium Risk
3.2.1 Unordered runtime schedule updates can roll back consensus rules and change them during
      block execution
Severity: Medium Risk.
Context: sink.rs#L41-L54.

Description: The runtime upgrade registry is a process-global map keyed only by L2 chain ID. Although
access is protected by an RwLock , an installed schedule does not include its L1 block number, block
hash, or schedule ID. Consequently, the lock makes individual writes atomic but does not prevent an
older request from overwriting newer state.
 crates/common/genesis/src/chain/upgrade.rs:429 unconditionally replaces the current overrides:


  pub fn replace_overrides(chain_id: u64, overrides: UpgradeActivationOverrides) {
    Self::write_registry().insert(chain_id, overrides);
  }


Similarly, crates/utilities/upgrade-signal/src/runtime/sink.rs:41 commits every completed re-
fresh without comparing its source against the currently installed schedule.
This permits the following ordering:
   1. Refresh A begins reading the schedule at L1 block 100.
  2. Refresh B begins reading the schedule at L1 block 101.
  3. B completes first and installs the newer block-101 schedule.
  4. A completes later and unconditionally replaces it with the stale block-100 schedule.
The reader pins contract calls to an L1 block hash, but the hash is discarded after the read. The
resulting crates/utilities/upgrade-signal/src/state.rs:13 retains only the block number, and
even that number is used only for reporting rather than commit ordering. The contract’s canonical
 scheduleId is not read.

Additionally, fork checks do not capture an immutable schedule. crates/execution/chainspec/sr
c/spec.rs:292 consults the process-global registry on every call. A refresh can therefore change
consensus rules during an operation that makes multiple fork checks.
A concrete example exists in block execution:



Cantina Managed                                   6                                  September 19, 2026
   • Before executing a transaction, the executor checks whether Jovian is active and calculates the
     transaction’s DA footprint at crates/common/evm/src/executor/block_executor.rs:230 .
   • After execution, it checks Jovian again before adding that footprint to the block total at
      crates/common/evm/src/executor/block_executor.rs:292 .

If a refresh occurs between these checks, the transaction can be evaluated under two different rule
sets. For example, Jovian can be inactive during the first check but active during the second, causing
the transaction to bypass the Jovian DA-footprint validation while committing a zero footprint.
Because refresh timing differs across nodes, one node may build or accept a block that another node
rejects under a consistent schedule. This can cause consensus divergence or a chain split.

Proof of Concept: The following deterministic test models a newer L1 read completing first and a
slower, older read completing afterward. It then demonstrates that live fork checks for the same block
timestamp return different results within one simulated operation.
Add the following test before the final closing brace of the existing #[cfg(test)] mod tests in
 crates/utilities/upgrade-signal/src/runtime/sink.rs :

3.2.2 Live monitor advances L1 baseline before apply, permanently suppressing failed auto-reapply
      (including incident delays)
Severity: Medium Risk.
Context: upgrade_signal.rs#L103-L116, upgrade_signal.rs#L165-L185, schedule.rs#L71-L88, re-
fresher.rs#L35-L57, state.rs#L70-L151.

Description: RuntimeAdmin live auto-apply is split across two steps that do not share failure seman-
tics.
 UpgradeSignalMonitor::poll reads L1, writes the observed values into states , and returns Some
(schedule) when any signal is Initialized or Changed . The EL observer and the CL actor then call
 UpgradeSignalRefresher::apply . apply validates the global minimumProtocolVersion attached
to every positive-timestamp signal and only then mutates RuntimeUpgradeRegistry .
If validation fails, the registry is unchanged but the monitor baseline has already moved. The next poll
compares against that poisoned baseline, classifies the same L1 values as Unchanged , and returns
  None . Auto-apply never retries. A later binary upgrade that would make the same schedule valid still
does not re-trigger the live path, because the baseline already holds those contract values.
The refresher documents that failed reads never advance the monitor baseline. That is true for read
failures. It is false for apply failures.
The version gate makes this operationally severe. Solidity minimumProtocolVersion is informational
and is not part of scheduleId ; the owner can bump it independently of timestamps. Rust treats it as
a hard gate on the entire schedule. validate_signal_supported_protocol_version skips the gate
only when activation_timestamp == 0 (clears). An incident delayTimestamp must keep a positive
timestamp, so a delay of an already-supported fork is rejected on an old binary whenever the global
minimum has been raised.
Honest composition:
  1. Owner raises minimumProtocolVersion because a new binary exists.
  2. Incident responder later delays an already-supported fork.
  3. An un-upgraded RuntimeAdmin node reads both changes, fails apply , poisons its baseline, and
     keeps the old activation.
  4. Upgraded nodes apply the delay. At the original timestamp the old node forks.
The node does not halt. It only warns and continues producing or validating with stale activations.
Metrics also record the observed (rejected) signal before apply, so dashboards can show the delayed
timestamp as if it had been adopted.

Proof of concept:   Integration test in crates/utilities/upgrade-signal/src/state.rs ( monitor_
does_not_reoffer_schedule_after_failed_apply ). It pins explicit protocol versions (so a workspace
  0.0.0 / U256::MAX binary cannot mask the gate), commits the rejected schedule into the monitor
baseline, shows apply fails without mutating the registry, shows the next observation is Unchanged
/ not requires_apply , and shows that even after the binary gains support the live monitor still will
not re-offer the same L1 values.

3.2.3   Runtime schedule application accepts past activation timestamps and clears already-active
        upgrades
Severity: Medium Risk.
Context: upgrade_signal.rs#L103-L116, upgrade_signal.rs#L165-L185, refresher.rs#L39-L57, sink.rs#L41-
L104.

Description:


Cantina Managed                                  10                                 September 19, 2026
Summary: RuntimeAdmin applies L1 upgrade schedules with no check against the node's current L2
head. An honest pre-activation clear or delay that is observed after L2 has already crossed the old
activation timestamp rewrites fork interpretation for blocks the node has already produced, because
runtime overrides take precedence for all timestamps.

Details: The only validation applied to a live schedule before it mutates a running node's fork configu-
ration is the protocol-version check in UpgradeSignalRefresher::apply . apply_schedule_to_sink
then writes every signal unconditionally through UpgradeActivation::from_timestamp .
There is no check that an activation timestamp is in the future relative to the node's current head,
that an already-active upgrade is not being cleared, or that the new value for an already-activated
upgrade equals the value the node has been running with.
In RuntimeAdmin mode this happens automatically: the CL actor and the EL node-started task call

3.4.2      Development builds bypass protocol-version compatibility checks
Severity: Informational.
Context: mod.rs#L49-L51, schedule.rs#L47-L49.

Description: The workspace uses version 0.0.0 for ordinary source, development, and CI builds.
The upgrade-signal implementation converts this version into U256::MAX , intending to prevent de-
velopment builds from being rejected.
Compatibility is then determined by checking whether the required protocol version is less than or
equal to the node’s advertised version. Because every U256 value is less than or equal to U256::MAX ,

Consequently, a source-built, CI, release-candidate, or incorrectly versioned binary running in startup-

application is opt-in. Nevertheless, the potential impact includes a chain split, making it a good-to-fix
issue.

features implemented by the binary, independently of its Cargo package version.

should also reject schedules containing unknown future upgrades instead of ignoring them.
If development environments require a bypass, place it behind a conspicuous unsafe option restricted
to development builds or development chains, with prominent warnings and metrics.
